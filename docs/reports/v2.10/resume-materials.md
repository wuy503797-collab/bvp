### Python 开发方向

**BVP Solver v2.10｜Python / PyQt5 数值应用工程化**

## 2. 30 秒项目介绍

这是我持续迭代的边值问题求解器项目，v2.10 是目前一个稳定工程快照。它支持打靶法和参数
延拓，并提供 PyQt5 GUI 与无 GUI API。项目最关键的改进是把“优化器结束”和“数学解通过”
分开：候选参数必须重新积分并通过边界残差、有限性和算法状态验收。我还建立了 285 项测试、
解析解和制造解验证、AST 安全解析、请求快照、结构化导出、性能计数以及 Windows/Linux CI。
它主要用于教学和数值实验，我也明确保留了有限差分、固定延拓步和协作式取消等限制。

## 3. 2 分钟项目介绍

这个项目最初是一个常微分方程边值问题课程程序，能够通过打靶和参数延拓求未知初值，并在
PyQt5 界面绘图。后续审计时我发现一个数值软件里很典型也很严重的问题：优化器报告停止，
不代表边界条件真正满足，甚至无实根问题也可能被错误包装成成功。

我先用严格 xfail 和负向 fixture 固化缺陷，再把成功判据改为 IVP 成功、所有数值有限、边界
逐分量通过和算法状态成功四者同时成立。候选参数还要经过一次独立构造的最终积分，重新计算
原始边界残差。为了不只验证“程序没报错”，我加入指数和简谐振子解析解、三次多项式制造解，
比较参数误差、最大/RMS 状态误差、边界残差和 ODE 一致性指标；目前完整回归是 285 项通过、
0 warnings。

工程上，我把数值核心从 GUI 迁入不依赖 PyQt5 的 `bvp_core`，用不可变请求快照解决切换任务、
旧线程信号和绘图记录污染；不同初始猜测和其他数值输入的结果现在能保持独立并共同显示。
表达式输入通过 AST 白名单直接构造 SymPy，导出使用严格 JSON 和原子替换。性能方面，我用
计数器证明一段变分积分没有参与 Jacobian，删除后 26.1 延拓的 IVP 调用从 874 降到 600，
结果保持等价。最后建立 Windows、Ubuntu 和精确依赖 CI。

这个项目让我形成的主要方法是：正确性要有数值 oracle 和负向证据，异步 GUI 要有来源模型，
性能优化要先量化再删除。当前仍有前向差分、固定步延拓、取消不能抢占单次积分等限制，仓库
LICENSE 也尚未决定。

## 4. STAR 案例

### 4.1 错误成功缺陷

**Situation：** 原实现可能把优化器终止直接展示为 BVP 成功，无实根或积分失败时存在误导。<br>
**Task：** 建立数学可解释的验收，并保留失败诊断而不是只抛异常。<br>
**Action：** 先用无实根、奇异 IVP 和过定约束测试复现；将验收拆成 IVP、有限性、边界和算法
四个门；对候选参数重新积分并计算原始残差；修复后移除严格 xfail，使测试成为普通 PASS。<br>
**Result：** 无实根返回 `success=False`、残差范数 1；奇异问题返回 `ivp_failed`、
`ivp_status=-1`、`ivp_t_final≈0.5`；有效算例保持通过。<br>
**Reflection：** 第三方库的 `success` 只能解释该库自己的停止条件，领域层必须建立独立验收。

### 4.2 数值验证体系

**Situation：** 只有 smoke test 和边界残差无法说明整条轨迹正确。<br>
**Task：** 为参数、状态、ODE 一致性和容差敏感性建立可重复 oracle。<br>
**Action：** 选择指数与简谐振子解析解，构造三次多项式制造解；统一计算参数误差、最大/RMS
状态误差、边界残差和 dense-output Simpson defect，并比较方法与重复运行。<br>
**Result：** 制造解最大状态误差 `2.22e-15`；解析算例最大状态误差约 `5.28e-09`；专项验证与
285 项完整测试通过。<br>
**Reflection：** defect 是独立构造的一致性指标但仍依赖 dense output，应避免把它说成严格
后验误差界。

### 4.3 表达式安全

**Situation：** GUI 和 JSON 接受用户数学字符串，通用解析器可能扩大到代码执行或属性访问。<br>
**Task：** 在保留教材表达式兼容的同时建立最小数学语言。<br>
**Action：** 先 `ast.parse(mode="eval")`，验证节点、运算符、函数、常量、上下文符号和复杂度，
再逐节点直接构造 SymPy；用攻击输入和全部持久化任务做双向回归。<br>
**Result：** 生产路径无 `eval/exec/parse_expr/sympify`，允许表达式和阻断样例均按预期通过，
所有现有任务保持兼容。<br>
**Reflection：** 输入安全与数值可解性必须分层；安全 parser 不应吞掉模型维数或积分错误。

### 4.4 GUI 请求竞态与绘图污染

**Situation：** 求解在线程中运行，用户可在完成前切换任务或修改猜测；历史曲线若引用当前
输入或可变 dense solution，会出现旧图随新输入改变。<br>
**Task：** 让结果永久绑定启动时事实，并安全处理旧信号、重复信号和关闭。<br>
**Action：** 引入不可变 `SolveRequest`、唯一 request/run ID 和稳定 signature；成功才创建
`SolveRecord` 并冻结曲线采样；对 stale/duplicate signal、取消与 close wait 加防护。<br>
**Result：** 同一问题三个猜测可形成 3 个独立记录并共同绘图；回归还覆盖 ODE、边界、终止
时间、IVP 方法、求解方法和容差变化，285 项测试全部通过。<br>
**Reflection：** GUI 异步正确性需要 provenance 数据模型，不能只靠按钮禁用或线程顺序假设。

### 4.5 性能热点

**Situation：** continuation 的 `_dPhi_dp` 积分了变分矩阵，但结果未进入最终有限差分
Jacobian，同一 Newton 步还重复计算当前残差。<br>
**Task：** 先证明工作无效，再在不改变公式的前提下删除。<br>
**Action：** 增加 IVP、nfev、Phi、Jacobian 和变分调用计数；构造同进程 before/after；删除
未消费的变分积分并复用 `Phi_current`；比较 Jacobian、参数、残差和导出元数据。<br>
**Result：** 26.1 continuation 的 IVP `874→600`、nfev `131732→94200`，Jacobian 最大差 0，
残差仍为 `1.0192e-11`。历史机器约 35.5%，本次机器约 28.3%。<br>
**Reflection：** 时间数据易受环境影响，CI 应守确定性计数和等价性契约而不是固定百分比。

### 4.6 干净环境与 CI

**Situation：** 在开发机通过不能证明依赖声明、GUI 离屏或跨平台可复现。<br>
**Task：** 建立本地统一入口和真实远端 Windows/Linux 验证。<br>
**Action：** 在范围依赖和精确参考依赖两个独立环境重建；统一执行 pip check、无警告导入、
compileall、pytest 和专项脚本；配置 3 个 GitHub Actions jobs，禁止 `continue-on-error`。<br>
**Result：** 本地、两个干净环境、Phase 11 分支 CI 和合并后 `main` CI 全部 PASS；285 tests，
GUI offscreen 未跳过，0 warnings。<br>
**Reflection：** CI 配置文件存在不等于 CI 已通过，报告只能引用真实 run；LICENSE 状态也必须
与代码质量状态分开。

## 5. 面试追问与回答要点

### 1. 为什么不用 `scipy.solve_bvp`？

项目来源于打靶法与参数延拓教学任务，目标包含未知初值参数、优化器行为和多分支观察，因此
保留 shooting/continuation 有教学价值。`solve_bvp` 是合理替代或对照工具，但换算法会改变
项目研究对象；未来可作为独立交叉验证，不能声称当前已经使用。

### 2. 为什么 optimizer success 不够？

优化器的成功只说明满足它自己的停止条件。积分可能失败、值可能非有限、边界残差可能仍大，
或算法外层延拓失败。领域成功必须重新验证轨迹和原始边界条件。

### 3. 如何证明结果正确？

不能对通用非线性 BVP 给出一次性绝对证明。当前使用解析解/制造解 oracle、参数和状态误差、
边界残差、ODE defect、容差敏感性、方法比较、重复性和负向问题组成证据链，并明确限制。

### 4. 制造解是什么？

先选择一个希望得到的真解，再反向构造 ODE、源项和边界条件，使该函数严格满足问题。这样可
为没有现成教材解析解的离散实现建立可控 oracle。

### 5. ODE defect 是什么？

它比较相邻采样状态增量和对 ODE 右端的 Simpson 积分近似，衡量轨迹与方程的一致性。它仍用
积分器 dense output，所以不是完全外部验证，也不是严格后验误差界。

### 6. 为什么使用 shooting？

它把 BVP 转成未知初值参数的有限维根问题，可复用成熟 IVP 和优化器，概念直观、适合教学。
缺点是对猜测、敏感性、奇异性和刚性可能不稳。

### 7. continuation 如何工作？

从初始猜测处容易满足的同伦残差逐步过渡到原始残差；每个固定步用阻尼 Newton 和前向差分
Jacobian 求修正。任一步失败会传播，结束后仍对原始问题重新验收。

### 8. 为什么 Jacobian 仍用有限差分？

它对用户定义表达式通用，实现与验证边界清晰。代价是多次 IVP 和尺度/舍入敏感。解析或自动
微分 Jacobian 是未来方向，但需要对正确性、性能和奇异问题重新建立证据。

### 9. 为什么可以删除变分积分？

代码和计数证明变分矩阵 `XT` 没有参与返回 Jacobian，后续仍逐参数调用 `_Phi` 做有限差分。
同进程对照显示返回 Jacobian 最大差为 0，而每次 Jacobian 的变分 IVP 从 1 变为 0。

### 10. 如何处理无解？

无法一般性证明无解，但候选点若不能通过原始边界容差就返回失败。无实根 fixture 固定验证
优化器不能把残差范数 1 的候选包装成成功。

### 11. 如何处理多解？

不同猜测和方法可能落在不同分支。每次请求独立记录并允许兼容曲线共同绘图。26.1 已得到两个
满足终端约束的分支，但不宣称枚举全部解。

### 12. 如何处理奇点？

检查 `solve_ivp.success/status/t_final`，保存失败诊断且不进入成功历史。当前奇异 fixture 在
`t≈0.5` 停止并返回 `ivp_failed`。软件不自动越过或正则化奇点。

### 13. 表达式如何避免代码执行？

只用 `ast.parse` 生成树，完整白名单通过后按允许节点直接构造 SymPy。属性、下标、私有名称、
未知调用等被拒绝；生产输入路径没有 Python `eval/exec` 或通用 SymPy 字符串解析旁路。

### 14. 为什么取消不能即时完成？

Python 层只能在自有控制点检查 token。正在执行的单次 SciPy `solve_ivp` 调用没有安全的线程
抢占接口，因此要等它返回；强杀线程可能破坏状态和资源。

### 15. GUI 如何避免错任务结果？

启动时冻结请求，worker signal 携带 request ID；GUI 只处理当前且未处理过的终态。记录保存
请求、结果和冻结曲线，后续切换任务或修改输入不改变历史。

### 16. `boundary_scales` 是什么？

它为每个边界分量提供量纲/典型大小，门槛为 `atol + rtol*scale_i`。它只用于最后验收，不
改变优化残差；错误 scale 可能使门槛不合理，因此需用户明确给出。

### 17. 为什么拆 `eps`？

一个值同时控制 IVP、root、least-squares、continuation、Jacobian 和边界验收会让语义耦合，
改一个过程就无意改变其他过程。v2.10 保留 legacy 映射，但允许显式独立配置。

### 18. 如何做性能验证？

先增加调用与 nfev 计数，固定代表算例，做同进程 before/after，对照 Jacobian、参数、轨迹、
残差和导出元数据；本地再用预热、重复中位数和 profile 补充观察。

### 19. 为什么不以耗时做 CI 门槛？

共享 runner、操作系统、CPU 调频和依赖版本都会影响时间。CI 检查 IVP/Phi/变分计数、数值
等价和计数器契约；耗时只做趋势证据。

### 20. 为什么 Windows/Linux 都测试？

项目包含 PyQt5、文件原子替换、路径处理、编码和 SciPy 二进制依赖，这些行为存在平台差异。
双平台加精确参考依赖能同时发现声明范围问题和环境漂移。

### 21. 项目最大的限制是什么？

数值上是 shooting/固定步 continuation 对敏感性、刚性与多分支的覆盖有限；验证上部分教材
问题没有解析真值；交互上取消不能抢占单次积分；发布上 LICENSE 尚未决定。项目适合教学和
实验，不适合安全关键决策。

### 22. 为什么 `problem_signature` 会因初始猜测改变？

signature 表示一次问题快照的全部来源事实，包括会影响求解分支的猜测。绘图兼容性另用坐标
语义判断，因此 signature 不同的猜测分支仍可共同显示，同时保持溯源差异。

### 23. 为什么 JSON 和 TXT 要同源？

如果各自拼装，字段或失败语义会漂移。先建立规范记录，再分别渲染严格 JSON 与人类摘要，
可以用同一测试验证来源、配置、运行信息和非有限值策略。

### 24. 285 项测试是否代表没有缺陷？

不代表。它说明已定义的契约和算例当前通过。测试集仍受 oracle、输入空间、平台和算法范围
限制；报告中的限制清单与负向用例是测试数字同等重要的解释条件。
