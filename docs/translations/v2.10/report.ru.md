## 3. Математическая модель

Рассматривается система первого порядка

\[
\dot{x}=f(t,x),\qquad t\in[t_0,T],\qquad x(t)\in\mathbb{R}^n.
\]

Неизвестная часть начального состояния задаётся параметром `p∈R^k`, а невязка краевых условий —

\[
\Phi(p)=R\!\left(x(t_0;p),x(T;p)\right),\qquad \Phi(p)=0.
\]

Реализация требует `len(R)=k` и проверяет это до SciPy. Даже при совпадении размерностей возможны
несколько решений, отсутствие решения, сингулярность, жёсткость и чувствительность к начальному
приближению. Успех программы подтверждает только прохождение данного численного пути через заданную
проверку, но не единственность и не полноту перечисления решений.

## 4. Метод стрельбы

```text
неизвестный p
→ полное начальное состояние
→ solve_ivp
→ Φ(p)
→ scipy.optimize.root(method="hybr")
→ при необходимости scipy.optimize.least_squares fallback
→ кандидат
→ отдельный итоговый solve_ivp
→ исходная краевая невязка
→ итоговая приёмка
```
Поле успеха `root` или `least_squares` описывает процесс оптимизации, а не математическое выполнение BVP.
Оптимизатор может остановиться по шагу, градиенту или лимиту при неприемлемой невязке, а задача Коши у
кандидата может завершиться отказом или неконечными значениями. Поэтому

```text
optimizer_success != BVP success
```

Итоговая проверка не переиспользует потенциально неполную последнюю траекторию оптимизатора, а заново
интегрирует и вычисляет исходные краевые условия.

## 5. Метод продолжения по параметру

Продолжение строит гомотопию от невязки, легко удовлетворяемой при начальном приближении, к исходной
невязке и проходит фиксированное число шагов. Каждый шаг использует демпфированный метод Ньютона.
Jacobian вычисляется прямой конечной разностью; линейная система решается напрямую или методом
наименьших квадратов. Демпфирование последовательно уменьшает шаг, пытаясь снизить невязку.

Отказ шага, Newton, конечной разности или задачи Коши явно передаётся. После всей гомотопии исходная
задача всё равно проходит отдельный IVP и краевую проверку. В v2.10 нет продолжения по псевдодуге,
адаптивного шага или аналитического Jacobian по параметрам.

## 6. Итоговый критерий успеха

```text
success =
    ivp_success
    AND finite_success
    AND boundary_success
    AND algorithm_success
```

- `ivp_success`: отдельная итоговая задача Коши достигла конца;
- `finite_success`: параметры, время, состояния и невязки имеют правильную форму и конечны;
- `boundary_success`: каждая компонента невязки проходит свой допуск;
- `algorithm_success`: метод стрельбы или продолжения не завершился отказом;
- `optimizer_success`: только диагностический статус.

Отказы имеют структурированные статусы `ivp_failed`, `non_finite_result`, `optimizer_failed`,
`boundary_residual_too_large` или `continuation_failed` и не входят в успешную историю.

## 7. Допуски и масштабированная проверка границы

| Поле | Назначение |
|---|---|
| `ivp_rtol`, `ivp_atol` | относительный/абсолютный контроль `solve_ivp` |
| `root_tol` | допуск остановки `root` |
| `least_squares_ftol`, `least_squares_xtol`, `least_squares_gtol` | остановка fallback |
| `continuation_residual_tol` | порог невязки Newton в продолжении |
| `jacobian_relative_step` | шаг прямой конечной разности |
| `boundary_atol`, `boundary_rtol` | итоговая абсолютная/относительная проверка |
| `boundary_scales` | покомпонентные масштабы итоговой проверки |

Совместимое `eps` сохраняет старое отображение, но явные поля разделяют процессы. Компонента принимается,
если

\[
|\Phi_i|\le a_{\mathrm{tol}}+r_{\mathrm{tol}}s_i.
\]

`boundary_scales` не меняет исходную невязку оптимизатора и не выполняет скрытое взвешивание. Масштабы
задаёт пользователь по размерности величин. Ужесточение одного допуска не гарантирует строго монотонного
изменения наблюдаемой ошибки или числа вызовов.

## 8. Ограниченный язык математических выражений

```text
строка пользователя
→ ast.parse(mode="eval")
→ полный белый список AST и проверка сложности
→ прямое построение SymPy по узлам
→ lambdify(modules="numpy")
```

Производственный вход не использует `parse_expr`, `sympify`, Python `eval` или `exec`. Разрешены только
явно перечисленные операции, функции, константы и символы контекста; атрибуты, индексы, приватные и
неизвестные имена отклоняются. Ограничиваются длина, число узлов, глубина, цифры, вызовы и степени.

Безопасный разбор означает лишь принадлежность выражения языку. Он не гарантирует интегрируемость ОДУ или
существование BVP. Синтаксическая безопасность, численная интегрируемость и разрешимость — разные уровни.

## 9. Архитектура программы

```text
GUI / JSON
    ↓
Dataset / adapters
    ↓
BVPProblem + SolverConfig
    ↓
bvp_core public API
    ↓
Restricted Expression Parser
    ↓
BVPSolver
    ↓
BVPResult
    ↓
SolveOutcome / SolveRecord
    ↓
Plot / Export / GUI
```

`bvp_core` содержит модели, конфигурацию, парсер, решатель, результат, запросы, наблюдаемость, счётчики и
сериализацию. Он не импортирует `main`, PyQt5 и не создаёт `QApplication`. `main.py` отвечает за старый
`Dataset`, GUI, worker, графики и взаимодействие. Численный решатель имеет одну реальную реализацию в
`bvp_core.solver`.

## 10. Жизненный цикл запроса и изоляция графиков

Каждое решение фиксируется в неизменяемом `SolveRequest` с `request_id`, задачей, конфигурацией и
метаданными. Стабильный `problem_signature` связывает математические факты, а `RunContext` создаёт новый
`run_id`. `SolveOutcome` различает completed, failed и cancelled; только успех становится `SolveRecord`.

GUI принимает только терминальный сигнал текущего запроса, игнорирует устаревшие и повторные сигналы.
Редактирование не меняет запущенный запрос. График берёт замороженную кривую записи, не текущий редактор и
не изменяемый dense output. Тесты подтверждают совместный показ ветвей одной задачи после изменения
начального приближения, а также независимость результатов после изменения ОДУ, границы, времени, метода и
допусков. Несовместимые координатные семантики исключаются явно.

## 11. Семантика отмены

Отмена кооперативна. Проверки находятся около разбора, этапов метода стрельбы, шагов продолжения и итоговой
приёмки. Выполняемый отдельный `solve_ivp` нельзя немедленно прервать из Python-потока; запрос завершается
на ближайшей точке после возврата. При закрытии окно просит отмену и ограниченно ждёт; при таймауте оно
остаётся открытым. `QThread.terminate()` не используется.

## 12. Наблюдаемость

`RunContext`, `RunMetadata` и `SolverCounters` связывают запуск с `run_id`, `request_id` и
`problem_signature`. Метаданные содержат UTC-время, длительность `perf_counter`, статус, метод, допуски,
версии Python/NumPy/SciPy/SymPy и доступные счётчики IVP, root, least-squares и continuation.

Ядро использует logger `bvp_core.events` со стандартным `logging` и только `NullHandler`. Оно не вызывает
`basicConfig`, не создаёт файл и не пишет по умолчанию в stdout/stderr. Приложение явно выбирает handler.
Одно измерение времени — диагностический факт, а не обещание производительности.

## 13. Единый контракт экспорта

JSON и TXT строятся из одного неизменяемого `CanonicalExportRecord` со схемой `bvp-result-v1`. Проблема и
конфигурация происходят из снимка `SolveRequest`, а не текущего GUI. Экспорт включает диагностику IVP,
оптимизатора, алгоритма, границы, источник и вспомогательные выходы.

JSON использует UTF-8, `ensure_ascii=False`, `allow_nan=False` и стабильный порядок; неконечные данные
представлены явно, а не нестандартными NaN/Infinity. TXT — читаемое резюме тех же фактов. Запись создаёт
временный файл в целевом каталоге, выполняет flush/`fsync`, затем атомарный `os.replace`.

## 16. Показатель численной согласованности ОДУ

Для интервалов dense output вычисляется defect типа Симпсона:

\[
D_i=y(t_{i+1})-y(t_i)-\frac{h_i}{6}
\left[f_i+4f_{i+1/2}+f_{i+1}\right].
\]

Он строится независимо от краевой невязки и поля `success` и заново вызывает исходное ОДУ. Однако
состояния в точках происходят из того же dense output `solve_ivp`. Это независимо сконструированный
показатель численной согласованности, а не полностью внешняя проверка интегратора и не строгая
апостериорная оценка погрешности.

## 18. Негативные тесты

**Нет вещественного корня.** Для `x(T)^2+1=0` метод стрельбы возвращает `success=False`,
`status=boundary_residual_too_large`, норму 1; продолжение возвращает `continuation_failed`, норму 1.

**Сингулярная задача Коши.** Для `x'=1/(t-0.5)` на `[0,1]` измерено:

```text
success = False
status = ivp_failed
ivp_status = -1
ivp_t_final = 0.499999999999952
boundary_residual_norm = inf
```

**Переопределённая граница.** Один неизвестный начальный параметр и две компоненты невязки отклоняются до
численного запуска с сообщением `unknown count != boundary residual count`.

## 22. Текущие ограничения и применимость

- Jacobian по параметрам остаётся прямой конечной разностью;
- continuation имеет фиксированные шаги, без адаптации и pseudo-arclength;
- выполняемый `solve_ivp` нельзя немедленно принудительно отменить;
- `boundary_scales` требует предметного масштаба от пользователя;
- GUI не содержит полного редактора всех расширенных допусков;
- у учебных задач 26.2–26.5 нет аналитической истины;
- для 26.1 проверены две ветви, но не перечислены все решения;
- Simpson ODE defect — показатель согласованности, не строгая оценка ошибки;
- фиксированные схемы чувствительны к приближению, сингулярности и жёсткости;
- проект предназначен для обучения и экспериментов, не для критичных по безопасности задач;
- `LICENSE` не определён, права использования нельзя предполагать;
- на историческом снимке ещё ожидалось отдельное решение по дублирующим JSON задач и пустым файлам
  совместимости.
