# Архитектура BVP Solver

[中文版本](architecture.zh-CN.md) · [Двуязычный указатель](README.md)

## 1. Границы слоёв

```text
GUI / JSON
    ↓
Dataset / adapters
    ↓
BVPProblem + SolverConfig
    ↓
bvp_core public API
    ↓
restricted expression parser → BVPSolver → BVPResult
    ↓
SolveOutcome / SolveRecord → Plot / Export / GUI
```

`bvp_core` является источником численной логики и не импортирует `main.py`, PyQt5 или Matplotlib.
`main.py` отвечает за совместимость старого `Dataset`, окна, worker, графики и взаимодействие. Импорт
ядра не создаёт `QApplication`, окно, файл журнала или вывод.

## 2. Модели ядра и точка входа

`BVPProblem` описывает уравнения, переменные, краевые условия, известные/неизвестные начальные значения
и интервал; `SolverConfig` — алгоритм и допуски; `solve_bvp_problem()` возвращает неизменяемый
`BVPResult`. Модели не меняются на месте, массивы результата представлены защитными копиями только для
чтения. Ошибка модели порождает `BVPValidationError`, а ожидаемый численный отказ возвращает результат с
`success=False`.

Основные обязанности разделены между `models.py`, `tolerances.py`, `expressions.py`, `solver.py`,
`api.py`, `results.py`, `observability.py` и `serialization.py`.

## 3. Запрос и жизненный цикл GUI

При запуске решения GUI фиксирует неизменяемый `SolveRequest` с уникальным `request_id`, задачей,
конфигурацией, идентичностью задания и метаданными отображения. Worker возвращает `SolveOutcome`; только
успешный исход становится `SolveRecord`. GUI принимает один терминальный сигнал активного запроса и
игнорирует устаревшие либо повторные сигналы.

График и экспорт читают замороженные переменные, время, кривые и источник записи, а не последующие правки
редактора. Поэтому совместимые результаты одной системы с другим начальным приближением, коэффициентами,
краевой целью, известным начальным значением, интервалом, методом решения, методом задачи Коши или
допусками сохраняются независимо и могут отображаться вместе. Несовместимая семантика координат явно
группируется или исключается.

## 4. Граница безопасности выражений

```text
string → ast.parse(mode="eval") → AST whitelist
       → direct SymPy construction → lambdify(modules="numpy")
```

Производственный вход строк не использует Python `eval`, `exec`, `parse_expr` или `sympify`. Белые списки
по контексту ограничивают символы, функции, константы, операции и сложность; атрибуты, индексы, lambda,
контейнеры, неизвестные и приватные имена отклоняются. Синтаксическая безопасность не равна численной
корректности: допустимое `1/(t-0.5)` всё равно вызывает отказ задачи Коши при пересечении полюса.

## 5. Наблюдаемость и связь запусков

Каждое реальное решение создаёт `RunContext`, затем неизменяемые `RunMetadata` и `SolverCounters`.
`run_id` обозначает запуск, `request_id` — запрос GUI, а `problem_signature` является стабильным SHA-256
нормализованного JSON задачи. Счётчики фиксируют IVP, nfev, `Phi`, Jacobian, оптимизатор и продолжение.

Ядро выдаёт структурированные события `logging` через `bvp_core.events` и устанавливает лишь
`NullHandler`. Приложение само выбирает handler; по умолчанию файл журнала не создаётся. Возможность
логирования не означает обязательного наличия файла на диске.

## 6. Контракт экспорта

JSON и TXT используют общий `CanonicalExportRecord` со схемой `bvp-result-v1`. Данные берутся из снимка
исходного запроса и соответствующего запуска, а не из текущего редактора GUI. JSON использует UTF-8,
`ensure_ascii=False`, `allow_nan=False`; неконечные диагностики нормализуются явно. Оба формата сначала
пишутся во временный файл того же каталога, выполняют flush/`fsync`, затем атомарно заменяют цель через
`os.replace`. TXT — читаемое резюме, JSON — машинный источник фактов.

## 7. Передача отказа и отмены

Для задачи Коши, конечности, оптимизации, продолжения и краевой проверки существуют явные статусы отказа.
Диагностика сохраняется, но результат не попадает в успешную историю. Отмена кооперативна: контрольные
точки есть около разбора, этапов алгоритма, шагов продолжения и итоговой проверки, однако выполняемый
вызов SciPy `solve_ivp` нельзя немедленно прервать из Python-потока. При закрытии окно запрашивает отмену
и ограниченно ждёт, не применяя `QThread.terminate()`.

## 8. Зависимости и границы обслуживания

Workflow CI охватывает Windows/Ubuntu с Python 3.11; подробности даны в
[документе о тестировании](testing.ru.md). Примечания GitHub Actions о Node.js 20→24 записаны в
[`docs/maintenance.md`](../maintenance.md) со статусом `DEFERRED`, `LOW_NON_BLOCKING`; это не дефект
алгоритма или теста. В репозитории нет `LICENSE`, поэтому готовность к выпуску ожидает решения о лицензии.
